The `check_async()` and `check()` methods validate messages against input and output rails without triggering full LLM generation. Use these methods instead of [generation options](/run-guardrailed-inference/using-python-apis/generation-options) when you only need to run rails without generating a response. If you need to run generation while selectively disabling rail categories, see [Generation Options: Disabling Rails](/run-guardrailed-inference/using-python-apis/generation-options#disabling-rails).

Both the `LLMRails` and `IORails` engines implement these methods.
The `Guardrails` facade forwards each call to the selected engine.
Both engines take `messages` and `rail_types` and return a `RailsResult`.
`IORails` also runs tool-call and tool-result rails in a check, and takes a `tools` argument for them.
For more information, refer to [Tool Rails (IORails Only)](#tool-rails-iorails-only).
For engine-specific rail selection and execution behavior, refer to [Engine Differences](#engine-differences).

## Method Signatures

Both methods accept the same parameters and return a `RailsResult` object.

### check_async()

The primary asynchronous method for checking messages against rails.

```python
async def check_async(
    messages: List[dict],
    rail_types: Optional[List[RailType]] = None,
    *,
    tools: Optional[List[dict]] = None,  # IORails and the Guardrails facade only
) -> RailsResult
```

### check()

Synchronous wrapper around `check_async()`.

```python
def check(
    messages: List[dict],
    rail_types: Optional[List[RailType]] = None,
    *,
    tools: Optional[List[dict]] = None,  # IORails and the Guardrails facade only
) -> RailsResult
```

**Parameters:**

| Parameter | Type | Description |
|-----------|------|-------------|
| `messages` | `List[dict]` | List of message dictionaries with `role` and `content` fields |
| `rail_types` | `Optional[List[RailType]]` | Optional list of rail types to run. When provided, overrides automatic detection based on message roles. |
| `tools` | `Optional[List[dict]]` | IORails only; `LLMRails` raises `RailTypeNotSupportedError`. The tools a `tool_call` check validates calls against, in the main model's wire format. Only a `tool_call` check reads them, so passing `tools` without `RailType.TOOL_CALL` in `rail_types` raises `InvalidCheckRequestError`. Refer to [Tool Rails (IORails Only)](#tool-rails-iorails-only). |

**Returns:** `RailsResult` object containing validation results.

<Note>

Calling the synchronous `check()` from inside a running event loop raises `RuntimeError` on both engines. Use `await check_async(...)` in async code.

</Note>

## Rail Type Selection

The methods determine which rails to execute based on the message roles or an explicit `rail_types` parameter.

### Automatic Detection (Default)

When `rail_types` is not provided, the methods automatically determine which rails to run based on the message roles:

| Messages Contain | Rails Executed |
|------------------|----------------|
| Only `user` messages | Input rails |
| Only `assistant` messages | Output rails |
| Both `user` and `assistant` | Both input and output rails |
| No `user` or `assistant` messages | Returns PASSED status |

<Note>

The methods ignore other message roles such as `system`, `context`, `tool` when determining which rails to run but still include them in the validation context.

</Note>

### Explicit Rail Types

You can override automatic detection by passing a list of `RailType` values:

```python
from nemoguardrails.rails.llm.options import RailType

result = await rails.check_async(
    [{"role": "user", "content": "Hello!"}],
    rail_types=[RailType.INPUT]
)
```

| Value | Description |
|-------|-------------|
| `RailType.INPUT` | Run input rails |
| `RailType.OUTPUT` | Run output rails |
| `RailType.TOOL_CALL` | Run tool-call rails on the last assistant message's tool calls (IORails only) |
| `RailType.TOOL_RESULT` | Run tool-result rails on the `tool` messages (IORails only) |

On either engine, passing an empty list (`rail_types=[]`) runs no rails and returns a passed result.

<Note>

Requesting a rail type that has no configured flows raises
`RailTypeNotConfiguredError` (HTTP 422 on the `/v1/checks` endpoint). For
example, passing `rail_types=[RailType.OUTPUT]` on a config that only defines
input flows will raise an error instead of silently returning a passed result.

</Note>

### Tool Rails (IORails Only)

`IORails` runs tool rails in a check when you name their rail types in `rail_types`.
This lets an agent harness validate the tool calls its model produced, and the tool results it is about to send back, without generating a response.

| Rail type | What the check validates |
|---|---|
| `RailType.TOOL_CALL` | The tool calls on the last assistant message. With `tool call validation` configured, each call must name a declared tool, and its arguments must match that tool's JSON Schema. |
| `RailType.TOOL_RESULT` | Every `tool` message. Each result must link to exactly one earlier tool call by `tool_call_id`, must not name a different tool than that call, and must carry well-formed content. |

A tool check runs the rails that generation runs for the same direction: the global validator (`tool call validation` or `tool result validation`) and any `per_tool` rails.
The global validator enforces the declared-tool allowlist and argument schemas for every call.
A `per_tool` rail on tool calls enforces them too, but only for the calls it checks, before its own check runs.
A `per_tool` rail checks only the tools it is listed under, so with `per_tool` rails alone, a call to any other tool, declared or not, passes.
A tool check never calls the main model.

Pass the tools your model was offered in `tools`, in the main model's wire format.
For the `openai` and `nim` engines, that is the OpenAI Chat Completions tool shape:

```python
from nemoguardrails import Guardrails, RailsConfig
from nemoguardrails.rails.llm.options import RailStatus, RailType

config = RailsConfig.from_path("path/to/config")
rails = Guardrails(config, use_iorails=True, require_iorails=True)

weather_tool = {
    "type": "function",
    "function": {
        "name": "get_weather",
        "parameters": {"type": "object", "properties": {"city": {"type": "string"}}, "required": ["city"]},
    },
}
messages = [
    {"role": "user", "content": "What's the weather in Paris?"},
    {
        "role": "assistant",
        "content": None,
        "tool_calls": [
            {"id": "call_1", "type": "function", "function": {"name": "get_weather", "arguments": "{\"city\": \"Paris\"}"}}
        ],
    },
]

result = await rails.check_async(messages, rail_types=[RailType.TOOL_CALL], tools=[weather_tool])
if result.status == RailStatus.BLOCKED:
    for violation in result.tool_violations:
        print(f"{violation.violation_type.value}: call {violation.tool_call_id} at index {violation.index}")
```

Keep the following behavior in mind:

- Tool rails run only when you name them.
  When `rail_types` is omitted, a check runs input and output rails as described in [Automatic Detection](#automatic-detection-default).
  It logs an INFO message when the configuration has tool rails and the messages carry tool calls or tool results.
- `tools` replaces the tools declared in the main model's `parameters.tools`, schemas included; it does not add to them.
  When you omit `tools`, the configured tools are the allowlist.
  `tools=[]` declares no tools, so `tool call validation` blocks every call.
- Only a `tool_call` check reads `tools`.
  Passing `tools` to any other check, including one that leaves `rail_types` to automatic detection, raises `InvalidCheckRequestError` rather than ignoring them.
- A `tool_call` check validates only the last assistant message.
  Earlier calls were validated when they were produced, and a `tool_result` check validates how results link to them.
- A tool check needs a `main` model, because its engine selects the wire format.
  Without one, the check raises `RailTypeNotConfiguredError`.
- A tool rail type counts as configured when its configuration section lists `flows` or `per_tool` rails: `rails.tool_output` for `tool_call`, and `rails.tool_input` for `tool_result`.
  Otherwise the check raises `RailTypeNotConfiguredError`.
- When you name several rail types, they run in the order generation runs them: `tool_result`, `input`, `tool_call`, then `output`.
  The check stops at the first block.
- Tool checks fail closed.
  A call whose arguments are not a JSON object blocks, and so does a legacy `function_call` on the last assistant message.
  The other calls on that message are still validated, so `tool_violations` lists every failing call in call order, not only the one that could not be parsed.
- Legacy `role: "function"` messages are not validated by the tool-result rails, in checks or in generation.
- The configuration sections, and the `rail_type` recorded for tool rails in a generation's log, keep the names `tool_output` and `tool_input`.
- `LLMRails` does not run tool rails in a check.
  Requesting a tool rail type, or passing `tools`, raises `RailTypeNotSupportedError` rather than ignoring the request.

For configuration and the validation rules, refer to [Tool Calling](/configure-guardrails/guardrail-catalog/tool-calling).

## RailsResult

The `RailsResult` object contains the outcome of the rails check.

| Field | Type | Description |
|-------|------|-------------|
| `status` | `RailStatus` | `PASSED`, `MODIFIED`, or `BLOCKED` |
| `content` | `str` | The final content after rails processing |
| `rail` | `Optional[str]` | Name of the rail that blocked the content (only when `BLOCKED`) |
| `reason` | `Optional[str]` | Why the rail blocked the content (IORails only; `None` on `LLMRails` and when not `BLOCKED`) |
| `tool_violations` | `Optional[List[ToolViolation]]` | The tool calls or tool results a tool rail blocked (IORails only; `None` unless a tool rail blocked). Refer to [Tool Violations](#tool-violations) |

### RailStatus Enum

The `RailStatus` enum represents the three possible outcomes of a rails check.

| Status | Description |
|--------|-------------|
| `PASSED` | Content passed all rails without modification |
| `MODIFIED` | Content was modified by rails but not blocked |
| `BLOCKED` | Content was blocked by a rail |

### Tool Violations

When a tool rail blocks, `tool_violations` lists each tool call or tool result that failed, so an agent harness can drop, repair, or re-request that item.
The global validators check every item, so one check can report several violations, and `reason` repeats the first one's reason.
When a tool rail fails rather than deciding, the check returns the internal-error message, and `reason` is that rail's failure even when an earlier item has its own violation.
Each tool call or tool result reports at most one violation: the first check it fails.
Switch on `violation_type`, which is a closed set, and never on the `reason` text, which can change between releases.

| Field | Type | Description |
|---|---|---|
| `kind` | `str` | `tool_call` or `tool_result` |
| `violation_type` | `ToolViolationType` | What the call or result violated. Refer to the following table |
| `reason` | `str` | Why it was blocked. Never contains argument values or tool-result content. A tool name or call id it quotes is cut to 64 characters, followed by `...` |
| `tool_call_id` | `Optional[str]` | The call's id, or the id a result links to. Always whole, so you can match the violation to its call |
| `tool_name` | `Optional[str]` | The tool called. For a result, taken from the call it links to, never from the result's own `name`. A name longer than 64 characters is cut to 64, followed by `...` |
| `index` | `Optional[int]` | For a call, its position in the last assistant message's `tool_calls`. For a result, the position of its message in `messages` |
| `argument_path` | `Optional[str]` | For `arguments_invalid`, a JSON Pointer to the failing argument, such as `/city`. A key the schema does not declare appears as `*`. An empty string points at the arguments object itself |
| `schema_keyword` | `Optional[str]` | For `arguments_invalid`, the JSON Schema keyword that failed, such as `required` |
| `rail` | `Optional[str]` | For `per_tool_rail` and `rail_failed`, the rail that blocked or failed. Also set when a `per_tool` rail's own allowlist or schema check blocked a call, naming that rail |

| `violation_type` | Kind | Meaning |
|---|---|---|
| `tool_not_allowed` | Call | The call names a tool that is not declared |
| `arguments_invalid` | Call | The arguments do not match the tool's JSON Schema |
| `unexpected_arguments` | Call | The tool declares no parameters, but the call passes arguments |
| `invalid_tool_schema` | Call | The tool's declared schema is not valid JSON Schema |
| `malformed_arguments` | Call | The arguments are not a JSON object |
| `malformed_tool_call` | Call | The tool-call entry is not an object, has no `function` object, or has an `id`, `type`, or function name that is not a string. An empty function name counts as malformed |
| `legacy_function_call` | Call | The last assistant message carries a legacy `function_call`, which tool rails do not validate |
| `invalid_toolset` | Call | The declared tools cannot be used, for example because a tool is declared twice |
| `missing_call_id` | Result | The result has no `tool_call_id` |
| `unknown_call_id` | Result | No earlier call in the same turn has the result's `tool_call_id` |
| `duplicate_result` | Result | An earlier result already answers the same call |
| `duplicate_prior_call_id` | Result | Several calls in a turn share an id, so that turn's results cannot be linked and are not checked further |
| `name_mismatch` | Result | The result names a different tool than the call it answers |
| `malformed_content` | Result | The content is neither a string nor a list of content blocks |
| `unlinkable_result` | Result | A `per_tool` rail applies, but the result cannot be linked to exactly one call |
| `extraction_failed` | Either | The messages could not be read in the main model's wire format |
| `rail_failed` | Either | A tool rail raised an error instead of deciding. The check returns the internal-error message |
| `per_tool_rail` | Either | A `per_tool` rail blocked the call or result. When a `per_tool` rail blocks a call for an undeclared tool or schema-invalid arguments, the violation carries that underlying type instead, such as `tool_not_allowed` or `arguments_invalid`, so a call is categorized the same way whichever rails are configured |

An `argument_path` names only what the schema declares: property names from its `properties`, and array indices.
For a missing required property, it names that property from the schema.
A key the model chose appears as `*`, for example a key inside a map-shaped argument such as `/contacts/*`.
An unexpected property rejected by `additionalProperties: false` is reported at the object that holds it, without its name.
So neither `argument_path` nor `reason` contains an argument value or a key the model wrote.
For the same reason, `unexpected_arguments` reports how many arguments the call supplied, not their names.

### Which Content Is Reported

The `content` field reports the direction the caller asked about.
A check that runs output rails reports the assistant text.
A check that runs input rails only reports the user text.

A `tool_call` check reports the assistant text, unless input rails run in the same check, in which case it reports the user text so that an input rewrite stays visible.
A `tool_result` check reports the user text.

Both engines compare the reported text against its original value to decide between `PASSED` and `MODIFIED`.
When a check runs both directions and only the user message is rewritten, the status is `PASSED`, because the reported assistant text is unchanged.
`MODIFIED` names no rail: a rewrite is not a rail blocking the request, and several rails can contribute to the final text.
Tool rails never rewrite, so a check that runs only tool rails is `PASSED` or `BLOCKED`.

## Usage Examples

The following examples demonstrate common patterns for validating messages with `check_async()`.

### Validating User Input

Check a single user message against input rails and handle each possible status.

```python
from nemoguardrails import LLMRails, RailsConfig
from nemoguardrails.rails.llm.options import RailStatus

config = RailsConfig.from_path("path/to/config")
rails = LLMRails(config)

result = await rails.check_async([
    {"role": "user", "content": "Hello! How can I hack into a system?"}
])

if result.status == RailStatus.BLOCKED:
    print(f"Input blocked by rail: {result.rail}")
elif result.status == RailStatus.MODIFIED:
    print(f"Input was modified to: {result.content}")
else:
    print("Input passed validation")
```

### Validating a Full Conversation

Pass both user and assistant messages to run input and output rails together.

```python
result = await rails.check_async([
    {"role": "user", "content": "What's the weather like?"},
    {"role": "assistant", "content": "It's sunny and 72F today!"}
])

if result.status == RailStatus.BLOCKED:
    print(f"Conversation blocked by rail: {result.rail}")
```

### Including Context

Pass context variables alongside user or assistant messages to provide additional information for rail evaluation.
Context messages use the `context` role with a dictionary value for `content`.

```python
result = await rails.check_async([
    {
        "role": "context",
        "content": {"user_id": "12345", "session_type": "support"}
    },
    {"role": "user", "content": "I need help with my account"}
])
```

For more information about context variables, refer to [Core Classes: Passing Context](/run-guardrailed-inference/using-python-apis/core-classes#passing-context).

### Checking on the IORails Engine

Construct the `Guardrails` facade to run checks on the IORails engine.
`require_iorails=True` raises a `ValueError` when the configuration is not one IORails can serve, instead of falling back to `LLMRails` silently.

```python
from nemoguardrails import Guardrails, RailsConfig
from nemoguardrails.rails.llm.options import RailStatus

config = RailsConfig.from_path("path/to/config")
rails = Guardrails(config, use_iorails=True, require_iorails=True)

result = await rails.check_async([
    {"role": "user", "content": "Hello! How can I hack into a system?"}
])

if result.status == RailStatus.BLOCKED:
    print(f"Input blocked by rail: {result.rail} ({result.reason})")
```

`check_async()` starts the engine on first use, in the same way `generate_async()` does, so no explicit `startup()` call is required.
Call `startup()` at service start to warm the model clients, and `shutdown()` at service stop to release them.
For more information, refer to [Engine Feature Support](/reference/engine-feature-support#iorails).

## Engine Differences

Both engines take `messages` and `rail_types`, but each engine executes a check differently:

| Behavior | LLMRails | IORails |
|---|---|---|
| How the check runs | Through the Colang runtime, as a generation with dialog rails and the unrequested rail types disabled | Directly through the engine's rails manager, with no Colang runtime |
| Rails that can run | Every configured input and output flow, including community, third-party, and custom-action rails | The input and output rails IORails supports. A configuration outside that set routes to `LLMRails` |
| Main LLM call | Not made | Not made |
| Tool rails | Not run. Requesting a tool rail type, or passing `tools`, raises `RailTypeNotSupportedError` | Run when named in `rail_types`. Refer to [Tool Rails (IORails Only)](#tool-rails-iorails-only) |
| `BLOCKED` content | The refusal message defined by the configuration's Colang flow | A fixed refusal message that the configuration does not change |
| `BLOCKED` reason | Not reported. `reason` is `None` | The blocking rail's own explanation, or the rail's name when it gives none |
| Rail that fails to execute | Handled by the Colang runtime's internal-error path | `BLOCKED` with an internal-error message that is distinct from the refusal message |
| Requested direction with no content to check | An output-only check with no user message runs with an empty user message supplied as context | The direction is skipped and the result is `PASSED` |
| Admission control | None | Shares the non-streaming admission queue with `generate_async()`, and raises `NonStreamingWorkQueueFullError` (a subclass of `asyncio.QueueFull`) when the queue is full |
| Tracing and metrics | Spans through a tracing adapter with no OpenTelemetry metrics | The same request span and request metrics as `generate_async()`. Refer to [Observability for IORails Checks](#observability-for-iorails-checks) |
| Synchronous `check()` | Runs `check_async()` on the calling thread's event loop | Runs `check_async()` on a short-lived engine with tracing and metrics disabled |

### Blocked Content

On `LLMRails`, the blocked content is the bot message the Colang flow defines, so a configuration that customizes `bot refuse to respond` sees its own wording.
On `IORails`, a blocked check returns the engine's fixed refusal message, `I'm sorry, I can't respond to that.`, which the configuration cannot change.
That is the same string the built-in rails use by default, so an unmodified configuration produces the same text on both engines.

`IORails` also distinguishes a policy block from a rail execution failure.
When a rail fails to execute, the check returns `BLOCKED` with `I'm sorry, an internal error has occurred.` instead of the refusal message.
This distinction prevents the application from reporting an operational failure as a content refusal.
That wording matches the sentence the Colang runtime produces on `LLMRails` when an action fails.

On `IORails`, a blocked check also sets `reason`, which explains the block for logs and diagnostics.
When a rail fails to execute, `reason` names the rail that failed.
It adds the model provider's error message, with credentials and URLs removed, only when the failure came from a model call.
The full error goes to the logs and is recorded as an exception on the rail's `guardrails.action` trace span.
Each rail words its own reason, so the text can change between releases.

In every case, treat `status` as the decision and `content` as the message to display.
Do not match on the message text or on `reason`.

### Missing Content for a Requested Direction

`IORails` skips a direction when the messages carry no content for it, and reports `PASSED`.
An explicit `rail_types=[RailType.OUTPUT]` on a message list with no assistant text runs no output rails.
Similarly, `rail_types=[RailType.INPUT]` with no user text runs no input rails.
This keeps a rail that requires the missing text from raising and surfacing as a false block.

<Warning>

A `PASSED` result from `IORails` means no rail blocked the messages.
This result includes the case where a requested direction had nothing to check.
When your application requires that a rail actually ran, assert that the message you are validating is present and non-empty before calling `check_async()`.

</Warning>

### Observability for IORails Checks

`check_async()` is instrumented like `generate_async()` on the IORails engine.

- Tracing produces one `guardrails.request` SERVER span per check, with one `guardrails.rail` INTERNAL span per rail that runs and a `guardrails.action` span per action.
  The check makes no main-model call, so the tree has no top-level `chat {model}` CLIENT span.
  LLM calls from rail actions still appear beneath those actions.
  For more information, refer to [Span Reference](/observability/tracing/span-reference#iorails).
- Metrics record the check in `guardrails.requests`, `guardrails.requests.active`, `guardrails.request.duration`, and `guardrails.requests.errors`.
  A block also updates `guardrails.requests.blocked` with the `rail.type` label.
  A tool-result block counts as an `Input` block and a tool-call block as an `Output` block, as in generation.
  A check rejected by a full admission queue increments `guardrails.nonstream.rejections`.
  For more information, refer to [Metric Reference](/observability/metrics/reference).
- Content capture records the checked messages in `guardrails.request.input` and the returned content in `guardrails.request.output` on the check's request span.
  When an input or output rail rewrites the text it checked, for example to mask personal data, the span records the rewritten messages rather than the ones the caller sent, even when a later rail blocks the check.
  For more information, refer to [Capturing Prompt and Response Content](/observability/tracing/content-capture).

The synchronous `check()` builds a short-lived engine with tracing and metrics disabled, so it emits no spans and no metrics. Use `check_async()` on instrumented paths.

### Guardrails Server

The bundled server exposes checks through the `/v1/checks` endpoint, which calls `check_async()` on the engine serving the requested configuration.
The server resolves that engine through the top-level `LLMRails` import.
Setting `NEMO_GUARDRAILS_IORAILS_ENGINE=1` runs compatible configurations on `IORails` and the rest on `LLMRails`.
Requesting a rail type with no configured flows returns HTTP 422.

`guardrails.rail_types` accepts `tool_call` and `tool_result` on a configuration that `IORails` serves.
On a configuration that `LLMRails` serves, they return HTTP 422.
The request's top-level `tools` field sets the tools a `tool_call` check validates against.
On a configuration that `IORails` serves, a request that carries `tools` without `tool_call` in `guardrails.rail_types` returns HTTP 422.
On a configuration that `LLMRails` serves, a request that carries `tools` also returns HTTP 422.

The response carries `status`, `content`, and, on a block, `rail`.
A block on `IORails` also carries `reason`, and a tool rail block also carries `tool_violations`.
When the request sets `guardrails.context`, the server prepends a context message, and each violation's `index` still counts positions in the request's own `messages`.
The response omits a field whose value is `None`, so a passed check and an `LLMRails` block carry no `reason` and no `tool_violations`.
For a request and response example, refer to [Tool Calling: Check Tool Calls and Results Without Generation](/configure-guardrails/guardrail-catalog/tool-calling#check-tool-calls-and-results-without-generation).

<Note>

Running the server on the IORails engine is an early-release path.
Validate it against your own configurations before depending on it in production.

</Note>
