# Migrating to 0.22

Starting with 0.22, `pip install nemoguardrails` no longer pulls LangChain or any provider-specific `langchain-*` packages. The library now ships with a built-in client that talks to OpenAI-compatible endpoints directly. LangChain remains available for engines whose API isn't OpenAI-compatible, but you opt in.

For most configurations the upgrade is silent. A few 0.21 shapes need a YAML rewrite. This guide covers each shape with a before/after recipe.

## Will my config keep working?

| Your 0.21 config | Action |
| --- | --- |
| `engine: openai`, `nim`, `nvidia_ai_endpoints`, `ollama` (no LangChain-style parameters) | No change. |
| `engine: vllm_openai` or any other LangChain wrapper for an OpenAI-compatible provider (DeepSeek, OpenRouter, Together.ai, Fireworks.ai, Groq, llama.cpp, ...) | YAML rewrite. See [Section 1](#section-1-openai-compatible-providers). |
| `engine: openai` with LangChain-only parameters (`openai_api_base`, `streaming`, `verbose`, `model_kwargs`, ...) | YAML rewrite. See [Section 2](#section-2-mixed-shape-configs). |
| `engine: anthropic`, `cohere`, `vertexai`, `google_genai`, `huggingface_*`, `trt_llm`, `self_hosted` (APIs that aren't OpenAI-compatible) | Opt into LangChain. See [Section 3](#section-3-falling-back-to-langchain). |
| `engine: azure`, `azure_openai` | OpenAI-compatible at the wire; pick the path that's easier for you. See [Section 3](#section-3-falling-back-to-langchain) for the LangChain default and the built-in alternative. |
| Custom provider registered in `config.py` via `register_chat_provider` | No change required; see [Section 4](#section-4-custom-providers). |

For the engine-by-engine matrix, see [Supported LLMs](../about/supported-llms.md).

## Section 1: OpenAI-compatible providers

Several 0.21 engines are LangChain wrappers for providers that already expose an OpenAI-compatible `/v1/chat/completions` route. In 0.22, talk to them directly through `engine: openai` with `parameters.base_url`. No LangChain install, no environment variable.

### Self-hosted vLLM

Before (0.21, `examples/configs/llama_guard/config.yml`):

```yaml
- type: llama_guard
  engine: vllm_openai
  parameters:
    openai_api_base: http://localhost:5000/v1
    model_name: meta-llama/LlamaGuard-7b
```

After (0.22):

```yaml
- type: llama_guard
  engine: openai
  model: meta-llama/LlamaGuard-7b
  parameters:
    base_url: http://localhost:5000/v1
    api_key: EMPTY
```

When self-hosted vLLM does not enforce authentication, set `parameters.api_key` to any non-empty placeholder such as `EMPTY`. If your deployment requires a real token, replace it with that value or load it through `api_key_env_var`.

### Hosted OpenAI-compatible providers (DeepSeek, OpenRouter, Together.ai, Groq, Fireworks.ai, llama.cpp)

Before (0.21):

```yaml
- type: main
  engine: deepseek
  model: deepseek-reasoner
```

After (0.22):

```yaml
- type: main
  engine: openai
  model: deepseek-reasoner
  parameters:
    base_url: https://api.deepseek.com/v1
    api_key_env_var: DEEPSEEK_API_KEY
```

The same pattern applies to other hosted providers: pick the provider's OpenAI-compatible base URL and set the API key.

## Section 2: Mixed-shape configs

A 0.21 config that already uses `engine: openai` may pass LangChain-only parameters such as `openai_api_base`, `streaming`, `verbose`, `cache`, `callbacks`, `tags`, `metadata`, `model_kwargs`, or provider-prefixed credential aliases (`*_api_key`, `*_base_url`). The 0.22 client forwards `parameters` directly to the OpenAI-compatible HTTP request, and these keys are not part of the OpenAI wire shape.

Before (0.21):

```yaml
- type: main
  engine: openai
  model: gpt-4o-mini
  parameters:
    openai_api_base: http://localhost:8001/v1
    streaming: true
    verbose: true
```

After (0.22):

```yaml
- type: main
  engine: openai
  model: gpt-4o-mini
  parameters:
    base_url: http://localhost:8001/v1
```

Rename `openai_api_base` to `base_url`, drop the LangChain Python flags, and remove provider-prefixed aliases. Streaming continues to work; the `stream_async` API is unchanged.

## Section 3: Falling back to LangChain

If your engine's API is not OpenAI-compatible (Anthropic, Cohere, Vertex AI, Google Generative AI, in-process Hugging Face, TensorRT-LLM, generic LangChain self-hosted), keep using LangChain. The path is explicit:

```bash
pip install langchain langchain-<provider>
export NEMOGUARDRAILS_LLM_FRAMEWORK=langchain
```

Engine names in `config.yml` stay bare. There is no `langchain/<provider>` prefix syntax.

```yaml
- type: main
  engine: anthropic
  model: claude-3-5-sonnet-latest
  parameters:
    temperature: 0.0
```

To list every engine name LangChain recognizes:

```bash
NEMOGUARDRAILS_LLM_FRAMEWORK=langchain nemoguardrails find-providers
```

### Azure OpenAI

Azure is OpenAI-compatible at the wire level, so two paths work. Pick whichever fits your stack.

A typical 0.21 Azure config:

```yaml
- type: main
  engine: azure_openai
  model: gpt-4.1-mini
  parameters:
    base_url: "https://my-resource.openai.azure.com/"
    azure_deployment: gpt-4.1-mini
    api_version: 2024-12-01-preview
```

**LangChain path (convenient default).** `langchain-openai` provides Azure-specific helpers that handle the deployment-name URL pattern and `api-version` query string for you.

```bash
pip install langchain langchain-openai
export NEMOGUARDRAILS_LLM_FRAMEWORK=langchain
export AZURE_OPENAI_API_KEY=<your-key>
```

```yaml
- type: main
  engine: azure_openai
  model: gpt-4.1-mini
  parameters:
    azure_endpoint: "https://my-resource.openai.azure.com/"
    azure_deployment: gpt-4.1-mini
    api_version: "2024-12-01-preview"
```

`base_url` is renamed to `azure_endpoint`; everything else is alias-compatible.

**Built-in path (no LangChain).** `engine: openai` with the deployment baked into `base_url`, plus `default_query` and `default_headers`.

```yaml
- type: main
  engine: openai
  model: gpt-4.1-mini
  parameters:
    base_url: "https://my-resource.openai.azure.com/openai/deployments/gpt-4.1-mini"
    default_query:
      api-version: "2024-12-01-preview"
    default_headers:
      api-key: "<your-azure-key>"
```

Make sure `OPENAI_API_KEY` is unset in the environment when running this. Otherwise the built-in client adds a redundant `Authorization: Bearer` header alongside `api-key`.

## Section 4: Custom providers

If your 0.21 `config.py` registers a custom provider using `register_chat_provider("my_engine", MyClass)` or `register_provider("my_engine", MyClass)`, the call will still work. Registration applies to whichever framework is active for the process: the built-in client when no environment variable is set, or LangChain when `NEMOGUARDRAILS_LLM_FRAMEWORK=langchain`. Make sure your custom class matches the framework: a class implementing the `LLMModel` Protocol should be used with the built-in client, while a LangChain provider class should be used with LangChain.

For implementing a custom backend, see [Custom LLM Model](../configure-rails/custom-initialization/custom-llm-model.md). For implementing a whole alternative framework, see [Custom LLM Framework](../configure-rails/custom-initialization/custom-llm-framework.md).

## What didn't change

- **Tool calling.** Provider-side function and tool calling keeps working; `tools` and `tool_choice` parameters retain the same wire shape.
- **Custom providers.** `register_chat_provider` and `register_provider` calls in `config.py` keep working; see [Section 4](#section-4-custom-providers).
- **Caching, telemetry, callbacks, embeddings.** No 0.22 changes affecting these.

## Common errors

When a migrated config doesn't boot cleanly, the runtime error names the next thing to fix. For the common cases (no default `base_url`, unsupported parameter, framework registration), see [Troubleshooting](../troubleshooting.md#llm-framework-routing).
