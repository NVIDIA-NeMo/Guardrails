# Upgrading to 0.22: LLM Framework Transition

NeMo Guardrails 0.22 introduces a `DefaultFramework` that talks to OpenAI-compatible endpoints directly over `httpx`, with no LangChain dependency on the request path. As a result, `langchain` and the provider-specific `langchain-*` packages are now development-only dependencies of `nemoguardrails`.

The guiding principle is:

> **Prefer DefaultFramework whenever the underlying wire protocol is OpenAI-compatible.** Use LangChain only as the fallback for engines whose API is not OpenAI-compatible.

This guide explains how the routing works, when you need to install LangChain, how to migrate legacy `engine: vllm_openai` configs, and how to control the active framework.

## Your existing config keeps working

If your `config.yml` uses one of the four engines below, the upgrade is silent: the same `pip install nemoguardrails` install pulls everything you need, and your config does not change.

| Engine | Default base URL |
|---|---|
| `openai` | `https://api.openai.com/v1` |
| `nim` | `https://integrate.api.nvidia.com/v1` |
| `nvidia_ai_endpoints` | `https://integrate.api.nvidia.com/v1` (alias for `nim`) |
| `ollama` | `http://localhost:11434/v1` |

These engines are routed to `DefaultFramework`, which builds an `OpenAIChatModel` against an OpenAI-compatible HTTP endpoint. You can override the endpoint by setting `parameters.base_url` and the API key by setting `parameters.api_key` (or the engine-specific environment variable, for example `OPENAI_API_KEY`, `NVIDIA_API_KEY`).

```yaml
models:
  - type: main
    engine: nim
    model: meta/llama-3.1-70b-instruct
    parameters:
      temperature: 0.0
      max_tokens: 1024
```

No code change, no new install command.

## OpenAI-compatible self-hosted and third-party endpoints

Many providers expose an OpenAI-compatible `/v1/chat/completions` route. For all of them, the recommended migration is:

> Use `engine: openai` plus `parameters.base_url`. Do not use `engine: vllm_openai` and do not set `NEMOGUARDRAILS_LLM_FRAMEWORK=langchain`.

Examples that fall under this pattern:

- **vLLM** with the OpenAI-compatible API (`python -m vllm.entrypoints.openai.api_server`).
- **TGI** / **Hugging Face TEI** when deployed with `/v1/chat/completions` enabled.
- **OpenRouter** at `https://openrouter.ai/api/v1`.
- **Together.ai**, **Fireworks.ai**, **Groq**.
- **DeepSeek** at `https://api.deepseek.com/v1`.
- **llama.cpp** server with `--api`.
- Any other "OpenAI-compatible" self-hosted endpoint.

### Migrating a legacy `vllm_openai` config

If your old config looked like this:

```yaml
models:
  - type: main
    engine: vllm_openai
    model: meta-llama/Llama-3.1-8B-Instruct
    parameters:
      openai_api_base: http://localhost:5000/v1
```

Migrate to:

```yaml
models:
  - type: main
    engine: openai
    model: meta-llama/Llama-3.1-8B-Instruct
    parameters:
      base_url: http://localhost:5000/v1
      api_key: EMPTY
```

When self-hosted vLLM does not enforce authentication, set `parameters.api_key` to any non-empty placeholder such as `EMPTY`. If your deployment requires a real token, replace it with that value or load it through `api_key_env_var`. The legacy `engine: vllm_openai` form is still recognized by the LangChain framework, but for new configurations the DefaultFramework form above is preferred.

## When you need LangChain

Engines whose API is not OpenAI-compatible still require LangChain. To use them you must:

1. Install LangChain plus the provider-specific package yourself.
2. Set `NEMOGUARDRAILS_LLM_FRAMEWORK=langchain` for the process. Engine names in `config.yml` stay bare (`engine: anthropic`, `engine: cohere`, ...) — there is no `langchain/<provider>` prefix syntax.

Examples that genuinely need LangChain:

- `vertexai` (Google Vertex AI).
- `anthropic` (Anthropic Claude).
- `cohere`.
- `azure` (Azure OpenAI uses a deployment-name URL plus `api-version` query string that the DefaultFramework's OpenAI-compatible client does not currently support).
- `huggingface_pipeline` / `hf_pipeline_*` (in-process Python pipeline).
- `huggingface_hub`.
- `huggingface_endpoint` (default text-generation schema; if your endpoint exposes `/v1/chat/completions`, prefer the DefaultFramework `engine: openai` plus `parameters.base_url` instead).
- `trt_llm` (TensorRT-LLM in-process).
- `self_hosted` (LangChain self-hosted wrapper).

### Install command

```bash
pip install langchain langchain-<provider>
```

For example, to use Anthropic Claude:

```bash
pip install langchain langchain-anthropic
```

For Cohere:

```bash
pip install langchain langchain-cohere
```

For Azure OpenAI:

```bash
pip install langchain langchain-openai
```

The provider package list is the same as the LangChain integration list. See the [LangChain chat-model integrations](https://docs.langchain.com/oss/python/integrations/chat) page for the full set of community providers.

### Activating the LangChain framework

Once LangChain and the provider package are installed, set the environment variable so the framework registry routes through `LangChainFramework`, and use the bare engine name in `config.yml`:

```bash
export NEMOGUARDRAILS_LLM_FRAMEWORK=langchain
```

```yaml
models:
  - type: main
    engine: anthropic
    model: claude-3-5-sonnet-latest
    parameters:
      temperature: 0.0
```

The framework name is global to the process. If you previously used `engine: anthropic` or `engine: cohere` directly without setting the variable, that path now fails — `DefaultFramework` does not know about those engines. Set `NEMOGUARDRAILS_LLM_FRAMEWORK=langchain` before the process starts.

The legacy provider-named engines (`anthropic`, `cohere`, `vertexai`, `azure_openai`, `deepseek`, `huggingface_endpoint`, `huggingface_pipeline`, `huggingface_hub`, `trt_llm`, `self_hosted`, `vllm_openai`, ...) all keep working under the LangChain framework. No engine renames are needed; install the matching `langchain-<provider>` package and toggle the env var.

To see the full list of engine names the LangChain framework recognizes, run:

```bash
NEMOGUARDRAILS_LLM_FRAMEWORK=langchain nemoguardrails find-providers
```

## Choosing the active framework

NeMo Guardrails resolves the framework name in two places:

- The `NEMOGUARDRAILS_LLM_FRAMEWORK` environment variable, read once when the framework registry initializes. The default value is `default`.
- The `set_default_framework(name)` function, which mutates the registry at runtime.

### Environment variable

Set `NEMOGUARDRAILS_LLM_FRAMEWORK` before starting the process:

```bash
export NEMOGUARDRAILS_LLM_FRAMEWORK=langchain
nemoguardrails chat --config=path/to/config
```

Accepted values:

- `default` (default) - the new httpx-based path. Engines `openai`, `nim`, `nvidia_ai_endpoints`, `ollama`, plus any other OpenAI-compatible provider configured with `engine: openai` and `parameters.base_url`.
- `langchain` - all engine resolutions go through `LangChainFramework`. Useful when every model in your config is a LangChain provider.
- Any name you have registered yourself with `register_framework(name, instance)`.

### Programmatic switch

```python
from nemoguardrails import set_default_framework

set_default_framework("langchain")
```

`set_default_framework` raises `KeyError` if the name has not been registered and is not one of the lazy-loaded built-ins (`default`, `langchain`).

### Registering a custom framework

```python
from nemoguardrails import register_framework, set_default_framework
from my_pkg import MyFramework

register_framework("my-framework", MyFramework())
set_default_framework("my-framework")
```

`register_framework` raises `ValueError` if a framework with the same name is already registered.

## Common errors

### "No default base_url for provider 'X'"

```
ValueError: No default base_url for provider 'cohere'.
Set it explicitly in model parameters: parameters.base_url
```

This error comes from `_resolve_base_url` in `nemoguardrails/llm/frameworks/default.py`. It means the engine name you used (here `cohere`) is not in `DefaultFramework`'s routing table and is not an OpenAI-compatible endpoint.

**Fix:** either supply a `parameters.base_url` for an OpenAI-compatible endpoint, or set `NEMOGUARDRAILS_LLM_FRAMEWORK=langchain` and install `langchain-cohere` (the engine name in `config.yml` stays `cohere`).

### "Framework 'X' is already registered"

`register_framework` does not allow rebinding. Either pick a different name or, in tests, call the registry-reset hook before re-registering.

### "Unknown framework 'X'"

`set_default_framework` was called with a name that is not registered and is not one of the lazy built-ins `default` or `langchain`. Register the framework first, or correct the name.

### `Unsupported parameter '<name>'` (or `Unrecognized request argument`) on first call

0.22 forwards `parameters` from `config.yml` directly to the OpenAI-compatible HTTP client when an engine routes through `DefaultFramework`. Keys that LangChain accepted as Python flags (`streaming`, `disable_streaming`, `verbose`, `cache`, `callbacks`, `tags`, `metadata`, `name`, `model_kwargs`) and provider-prefixed credential aliases (`openai_api_base`, `nim_base_url`, `*_api_key`, ...) are not part of the OpenAI wire shape and are rejected by the provider. NeMo Guardrails detects the recognizable shapes at boot and on the first 400/422 response, and appends a hedged migration hint to the underlying provider error.

**Fix paths:**
- **Adapt the config to OpenAI-compatible shape.** Rename `openai_api_base` → `base_url`, drop LangChain Python flags, remove provider-prefixed aliases. The migration recipe in [OpenAI-compatible self-hosted and third-party endpoints](#openai-compatible-self-hosted-and-third-party-endpoints) covers the common case.
- **Keep the 0.21 config.** Set `NEMOGUARDRAILS_LLM_FRAMEWORK=langchain` for the process and install LangChain plus the matching provider package. The legacy field names continue to work under the LangChain framework.

## What does not change in 0.22

- **Streaming.** `stream_handler`, `stream_async`, and the rails-level `streaming` flag work the same as 0.21. No config changes required.
- **Tool calling.** `tools`, `tool_choice`, and provider-side function/tool calling continue to work. The `LLMResponse.tool_calls` shape is unchanged.
- **Reasoning configs.** `reasoning_config: {remove_reasoning_traces: ..., start_token: ..., end_token: ...}` is unchanged. Reasoning models (DeepSeek R1, NIM `nemotron-reasoning`, OpenAI o-series) keep working under both frameworks.
- **Custom providers registered in `config.py`.** Calls to `register_chat_provider(name, cls)` and `register_provider(name, cls)` continue to work. They register on the active framework — `DefaultFramework` if no env var is set, `LangChainFramework` if `NEMOGUARDRAILS_LLM_FRAMEWORK=langchain` is set. Providers registered for one framework are not visible to the other; if your `config.py` needs to support both modes, register on each:

  ```python
  from nemoguardrails.llm.frameworks import get_framework

  get_framework("default").register_provider("my_engine", MyLLMModelClass)
  get_framework("langchain").register_provider("my_engine", MyLangChainProviderClass)
  ```
- **Caching, telemetry, callbacks, embeddings.** No 0.22 changes affecting these.
